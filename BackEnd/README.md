# 수리공학 페스타 백엔드

구글폼 신청 내역과 카카오뱅크 입금 내역을 대조해 참가비 납입 여부를 확인한다.
그 뒤로 참가 확정 · 조 배정 · 당일 출석 · 럭키드로우가 이어진다.

## 왜 이런 구조인가

카카오뱅크 개인 계좌에는 공개 API가 없다. 자동화 경로를 차례로 검토했지만 모두 막혔다.

| 검토한 방법 | 결과 |
|---|---|
| 오픈뱅킹 API (금융결제원) | 사업자등록·이용기관 심사 필요 → 학생회는 불가 |
| 안드로이드 공기계 알림 포워딩 | **카카오뱅크가 유심 없는 기기의 로그인을 막는다 → 불가** |
| 스크래핑 대행 서비스 | 유료 + 계정 인증정보를 제3자에게 위임해야 함 |
| **거래내역 파일 업로드** | **채택.** 담당자가 앱에서 내려받아 관리자 페이지에 올린다 |

그래서 **입금 확인은 실시간이 아니다.** 담당자가 파일을 올린 시점까지만 반영된다.
이 사실을 숨기면 "돈 냈는데 미납으로 뜬다"는 문의가 쏟아지므로,
반영 시점을 공개 API(`/api/sync-status`)로 내보내 참가자 화면에 그대로 보여준다.

### 중복 제거

같은 기간을 다시 받아 올리는 일이 잦으므로(매번 '이번 달 전체'를 받는 식),
**지문(fingerprint)** 으로 중복을 흡수한다. 거래 후 잔액이 있으면 `(날짜, 금액, 잔액)`,
없으면 `(분 단위 시각, 금액, 입금자명)` 을 해시한다. 잔액은 원장에서 거의 유일한
지문이라, 기간이 겹쳐도 같은 건으로 인식된다.

### 알림 포워딩 경로

코드는 남아 있지만 `PUSH_INGEST_ENABLED=false` 로 **꺼져 있다.**
유심이 꽂힌 전용 기기를 마련하면 `true` 로 켜서 실시간 수집을 병행할 수 있다.
켜져 있을 때의 동작(원문 보관·재파싱)은 `tests/test_unparsed.py` 가 계속 검증한다.

## 매칭 엔진

입금자명 규칙(`이름+전화뒷4자리`)이 지켜지지 않을 것을 전제로 4단계 폴백을 둔다.

| 단계 | 조건 | 결과 |
|---|---|---|
| 1 | 이름 + 전화 뒷4자리 일치, 후보 유일 | 자동 연결 |
| 2 | 이름 일치, 후보 유일 + 금액이 미납액과 동일 | 자동 연결 |
| 3 | 동명이인 다수 / 금액 불일치 | `AMBIGUOUS` → 관리자 확인 |
| 4 | 이름 매칭 실패 | `UNMATCHED` → 관리자 확인 |

- 5,000원(총학생회비 납부자) / 7,000원(미납부자)의 **금액 차이 자체가 매칭 신호**로 쓰인다.
  다만 지난 행사(45,000 / 59,000)보다 금액이 작고 서로 가까워 **신호가 약해졌다.**
  뒤풀이비까지 얹히면 보낼 법한 금액이 셋으로 늘어난다 — '참가비는 두 겹이다' 절 참고.
- **입금 1건은 참가자 1명의 것이다.** 한 사람이 여러 명 몫을 한 번에 보내는 일은 없다고
  확인되어, 금액 조합을 역산해 합산 입금을 추측하지 않는다. 반대로 한 참가자가
  여러 번 나눠 내는 것(부분 입금 후 추가 입금)은 가능하다.
- 자동 매칭은 관리자의 수동 지정(`manual_locked`)을 절대 덮어쓰지 않는다.
- 입금이 폼 제출보다 먼저 도착해도, 폼이 들어오는 순간 미매칭 건을 자동 재매칭한다.

### 기타 입금 (소액 분리)

계좌를 참가비 전용으로 쓰지 않으면 1,500원짜리 잡음이 확인 필요 큐를 덮어버려
정작 봐야 할 건이 묻힌다. 그렇다고 버리면 "5천원 보냈는데요" 하는 문의에 답할 수 없다.
그래서 **버리지 않고 갈라 두기만 한다.**

**이름이 어떤 신청자와도 맞지 않으면서** `MINOR_DEPOSIT_THRESHOLD`(기본 10,000원)
미만인 입금은 `MINOR` 상태가 되어 확인 필요 큐에서 빠진다.

| 입금 | 결과 | 이유 |
|---|---|---|
| `박정현` 1,500원 | 기타 입금 | 이름 불일치 + 소액 |
| `정약용8888` 5,000원 | **확인 완료** | 이름+뒷4자리 일치 → 부분 입금으로 처리 |
| `유관순` 5,000원 | 판단 보류 | 이름은 맞음 → 사람이 봐야 함 |
| `학부모님` 90,000원 | 미매칭 | 금액이 커서 그냥 넘길 수 없음 |

- 관리자 페이지 → 입금 내역 → **기타 입금** 탭에서 언제든 볼 수 있다.
- **다시 검토** 버튼으로 확인 필요 큐에 되돌릴 수 있다.
- 소액을 먼저 보낸 사람이 나중에 신청서를 내면 자동으로 다시 꺼내온다.
- `MINOR_DEPOSIT_THRESHOLD=0` 이면 이 분리 자체를 끈다.

## 로컬 실행

```bash
cd BackEnd
python -m venv .venv
.venv/Scripts/activate        # Windows PowerShell: .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"   # SECRET_KEY
python -c "import secrets; print(secrets.token_urlsafe(32))"   # INGEST_TOKEN
python scripts/hash_password.py                                # ADMIN_PASSWORD_HASH (국장단)
python scripts/hash_password.py --staff                        # STAFF_PASSWORD_HASH (국원)

python wsgi.py     # http://127.0.0.1:8000
```

`.env` 는 `app/config.py` 가 import 될 때 로드된다. `Config` 클래스 본문이 import
시점에 `os.getenv` 를 읽기 때문에, 그보다 늦게 부르면 모든 값이 빈 문자열이 된다.

## 시놀로지 배포

1. `BackEnd/` 전체를 NAS 공유폴더에 올린다 (`.env` 포함, `.venv`·`data` 제외).
2. `.env` 의 `DATA_DIR=/data`, `CORS_ORIGINS` 에 실제 프론트 도메인을 넣는다.
3. **Container Manager > 프로젝트 > 생성** → 경로 지정 → `docker-compose.yml` 선택 → 빌드.
4. `docker-compose.yml` 의 `volumes` 를 실제 공유폴더 경로로 바꾼다.
   SQLite 파일(`mt.db`)이 여기 남으므로 **반드시 컨테이너 외부 볼륨이어야 한다.**
5. **DSM > 로그인 포털 > 고급 > 역방향 프록시** 에서
   `api.도메인` (HTTPS 443) → `localhost:<APP_PORT>` 로 연결하고 Cloudflare 인증서를 지정한다.

> **포트는 `docker-compose.yml` 의 `APP_PORT` 한 곳에서만 정한다.**
> gunicorn 이 이 값을 읽어 바인딩하므로, `ports`·`healthcheck`·역방향 프록시가
> 모두 같은 숫자를 써야 한다. 예전처럼 `ports` 만 바꾸면 컨테이너는 8000 을 듣고
> 있어 연결이 되지 않는다.
6. `https://api.도메인/api/health` 가 `{"status":"ok"}` 를 반환하면 완료.

> Cloudflare Pages(HTTPS)에서 HTTP 백엔드를 호출하면 mixed content 로 차단된다.
> 백엔드는 반드시 HTTPS 로 노출해야 한다.

### 코드를 고쳐 다시 배포할 때

컨테이너를 지우고 이미지를 다시 빌드해도 **데이터는 남는다.** 단, 두 가지가 지켜져야 한다.

**1. 볼륨 경로를 바꾸지 말 것**

`docker-compose.yml` 의 `volumes` 왼쪽 경로(NAS 실제 폴더)에 `mt.db` 와 백업이 들어 있다.
프로젝트 폴더 안(`./data`)보다 **프로젝트 밖의 독립 폴더**를 쓰는 편이 안전하다.
프로젝트를 삭제할 때 폴더째 지워지는 사고를 막을 수 있다.

**2. 빌드 실패 · 기동 실패 대처**

| 로그 | 원인 | 해결 |
|---|---|---|
| `Permission denied: '/app/gunicorn.conf.py'` | 시놀로지 공유폴더는 ACL 을 써서 POSIX 모드가 `000` 으로 보인다. `COPY` 가 그 모드를 그대로 가져와 파일을 못 읽는다 | Dockerfile 의 `chmod -R a+rX /app` 이 처리한다. **이미지를 다시 빌드**해야 반영된다 |
| `unable to open database file` | 볼륨 폴더를 uid 1000 이 쓸 수 없다 | `sudo chown -R 1000:1000 <볼륨경로>` |
| 포트는 열렸는데 연결 안 됨 | `APP_PORT` 와 `ports` 가 다르다 | 둘을 같은 숫자로 |
| `ADMIN_PASSWORD_HASH 가 비어 있어…` | `.env` 를 못 읽었다 | `.env` 가 `docker-compose.yml` 과 같은 폴더에 있는지 확인 |
| `STAFF_PASSWORD_HASH 가 비어 있습니다` | 국원용 비밀번호를 아직 안 넣었다 | 그대로 둬도 동작한다(모두 한 비밀번호). 나누려면 `python scripts/hash_password.py --staff` |

**3. 재배포 직후 로그를 확인할 것**

기동 시 이런 줄이 남는다.

```
INFO  DB 위치: /data/mt.db
INFO  보관 중인 데이터: participants 213 · deposits 198 · allocations 195
```

`participants 0` 으로 찍히면 볼륨이 안 붙은 것이다. **그 상태로 폼을 다시 동기화하지 말고**
먼저 경로부터 확인해야 한다. (0건이면 경고 로그도 함께 남는다)

### 모델을 바꿔도 기존 DB가 깨지지 않는다

관리자 페이지에서 어떤 정보를 다룰지 아직 확정되지 않아 **참가자 필드가 계속 늘어난다.**
그런데 `create_all()` 은 없는 테이블만 만들 뿐, 기존 테이블에 컬럼을 추가하지 않는다.
그대로 두면 필드를 하나 늘리는 순간 `no such column: participants.xxx` 로 죽는다.

그래서 기동할 때마다 모델과 실제 스키마를 비교해 **빠진 컬럼을 자동으로 채운다**
(`app/database.py` 의 `ensure_schema`).

- 컬럼 추가는 자동 (`ALTER TABLE ADD COLUMN`, 기본값까지 기존 행에 채움)
- **스키마를 건드리기 직전에 DB를 자동 백업**한다 (`data/backups/*-premigrate.db`)
- 컬럼 삭제·타입 변경은 데이터가 날아갈 수 있어 **하지 않고 로그로만 알린다**

즉 **필드는 마음 편히 늘려도 된다.** 지우는 것만 조심하면 된다.

> 새 폼 질문이 늘어난 정도라면 컬럼을 만들 필요도 없다.
> 매핑되지 않은 응답은 `extra_json` 에 그대로 담긴다.
> 관리자 화면에서 **검색·필터링해야 할 때만** 정식 컬럼으로 올리면 된다.

상태 확인:

```bash
docker exec gongdae-mt-backend flask db-info
# DB 위치 : /data/mt.db
# 행 수 : participants 213 / deposits 198 ...
# 스키마가 모델과 일치합니다.
```

### 백업

SQLite 파일 하나가 전부다. 스키마 변경 시에는 자동 백업되지만,
MT 기간에는 하루 한 번 수동으로도 남겨 두는 것을 권한다.

```bash
docker exec gongdae-mt-backend flask backup
# 백업 완료: /data/backups/mt-20260801-090000-manual.db
```

WAL 모드를 쓰므로 **파일을 직접 복사하면 최신 내용이 빠질 수 있다.**
위 명령은 체크포인트를 먼저 돌린 뒤 복사하므로 안전하다.
NAS 밖으로 옮길 때는 `data/backups/` 폴더를 통째로 가져가면 된다.

## 운영: 거래내역 업로드

이것이 입금 확인의 전부다. MT 접수 기간에는 **하루 1~2회** 돌리는 것을 권한다.

1. 카카오뱅크 앱 → 계좌 → 거래내역 → 조회기간 설정 → **내역 내려받기(엑셀)**
2. 관리자 페이지 → **거래내역 업로드** → 파일 선택
3. **확인 필요 / 미매칭** 건을 &lsquo;입금 내역&rsquo; 탭에서 손으로 처리

기간이 겹치게 받아도 된다. 이미 등록된 입금은 지문으로 걸러진다.
매번 &lsquo;접수 시작일 ~ 오늘&rsquo; 로 통째로 받는 편이 누락이 없어 오히려 안전하다.

### 비밀번호가 걸린 파일

내려받은 엑셀에는 열기 비밀번호가 걸려 있다. `.env` 의 `STATEMENT_PASSWORDS` 에
적어 두면 **잠긴 파일을 그대로 올려도 서버가 풀어서 읽는다.** 담당자가 매번
엑셀로 열어 비밀번호를 지우고 다시 저장하는 절차가 없어진다.

```
STATEMENT_PASSWORDS=파일비밀번호          # 쉼표로 여러 개도 가능
```

이 저장소는 공개되어 있으므로 **실제 비밀번호는 `.env` 에만** 둔다. 코드·문서·예시
파일 어디에도 적지 않는다.

- 여러 개를 두는 이유는 비밀번호를 바꾼 뒤에도 옛 파일을 다시 올릴 수 있게 하기 위함이다.
  앞에서부터 차례로 시도한다.
- 비워 두면 잠긴 파일은 &lsquo;비밀번호가 등록되어 있지 않다&rsquo;는 400 으로 거절된다.
  기능이 없던 때처럼 손으로 풀어 올리면 된다.
- 값을 바꾸면 **컨테이너를 다시 시작해야** 반영된다 (`.env` 는 import 시점에 한 번 읽는다).
- 잠긴 파일은 zip 이 아니라 OLE 복합문서라, 파서가 앞 8바이트를 보고 알아서 갈라 처리한다.
  확장자로 판단하지 않으므로 잠긴 파일과 푼 파일을 섞어 올려도 상관없다.

### 파일 형식

실물 파일은 A열이 비어 있고, 머리말 뒤 11행에 헤더가 온다.
파서가 헤더 위치를 자동으로 찾으므로 그대로 올리면 된다.

| 열 | 내용 | 쓰임 |
|---|---|---|
| 거래일시 | `2026.05.06 11:40:59` | 입금 시각 |
| 구분 | `입금` / `출금` | 출금은 버린다 |
| 거래금액 | `44,500` / `-120,000` | 입금액 |
| 거래 후 잔액 | `17,494,137` | **중복 제거 지문** |
| 거래구분 | `일반입금` / `체크카드결제` | 쓰지 않음 |
| 내용 | `홍길동5678` | **입금자명 — 매칭의 핵심** |
| 메모 | 자유 기재 | 원본에 보존 |

컬럼명이 조금 달라도 별칭 표(`app/parsers/statement.py` 의 `_ALIASES`)로 흡수한다.
`.xlsx` 와 `.csv`(utf-8 / cp949) 를 지원한다.

## 안드로이드 알림 포워딩 (현재 미사용)

> **카카오뱅크는 유심이 없는 기기에서 로그인이 되지 않는다.** 공기계만으로는
> 알림을 받을 수 없어 이 경로는 `PUSH_INGEST_ENABLED=false` 로 꺼져 있다.
> 아래는 유심이 꽂힌 전용 기기를 마련했을 때를 위한 안내다.

공기계에 **MacroDroid**(무료로 충분)를 설치하고 `.env` 에 `PUSH_INGEST_ENABLED=true` 를 넣는다.

1. 카카오뱅크 앱에서 **입금 알림을 켠다.**
2. 안드로이드 설정에서 MacroDroid 에 **알림 접근 권한**을 준다.
3. 설정 > 알림 > **알림 요약/그룹화를 끈다.** (여러 건이 묶이면 파싱이 깨진다)
4. MacroDroid 에서 매크로를 만든다.

   - **트리거**: 알림 → 알림 수신 → 애플리케이션: `카카오뱅크`
   - **액션**: 연결 → HTTP 요청
     - 방식: `POST`
     - URL: `https://api.도메인/api/ingest/deposit`
     - 커스텀 헤더: `X-Ingest-Token: <.env 의 INGEST_TOKEN>`
     - Content-Type `text/plain` + 본문 `[notification_text]` **(권장)**
       또는 `application/json` + 본문 `{"title":"[notification_title]","text":"[notification_text]"}`
     - 알림 문구에 큰따옴표·줄바꿈이 섞이면 JSON 이 깨지므로 `text/plain` 이 안전하다

5. 공기계 설정 (삼성 One UI 는 백그라운드 앱을 공격적으로 종료한다)
   - 배터리 최적화 **예외** 처리 (안 하면 며칠 뒤 조용히 죽는다)
   - 설정 > 배터리 > 백그라운드 사용 제한 > **잠자는 앱** 목록에서 제외
   - 상시 충전 + Wi-Fi 절전 해제

### 배선 점검 — `/api/ingest/ping`

포워더를 붙이는 동안에는 `deposit` 대신 **`ping`** 으로 먼저 쏘는 것을 권한다.
토큰·헤더·본문이 제대로 도착하는지, 그리고 그 알림이 **현재 규칙으로 해석되는지**까지
즉시 알려주면서 **아무것도 저장하지 않는다.** 몇 번을 눌러도 안전하다.

```bash
curl -X POST https://api.도메인/api/ingest/ping \
  -H "Content-Type: application/json" \
  -H "X-Ingest-Token: <INGEST_TOKEN>" \
  -d '{"title":"카카오뱅크","text":"입금 5,000원 홍길동5678 잔액 1,234,567원"}'
```

```json
{
  "ok": true,
  "message": "연결 정상입니다. 저장은 하지 않았습니다.",
  "bodyWasValidJson": true,
  "parse": { "ok": true, "depositorName": "홍길동5678", "amount": 5000, "balanceAfter": 1234567 }
}
```

`parse.ok` 가 `false` 면 연결은 됐지만 문구를 못 읽는 것이다. `parse.reason` 을 보고
`app/parsers/push.py` 의 패턴을 고치면 된다.

### 읽지 못한 알림은 버리지 않는다

알림 문구는 앱 버전에 따라 바뀐다. 해석에 실패한 알림을 버리면 입금 1건이 조용히
사라지므로, **원문을 통째로 보관**하고 `202` 와 사유를 돌려준다.

- 관리자 페이지 **&lsquo;읽지 못한 알림&rsquo;** 탭에서 실제 문구를 확인한다.
- 같은 문구가 반복 전송되어도 행이 불어나지 않고 수신 횟수만 올라간다.
- `app/parsers/push.py` 를 고친 뒤 **&lsquo;지금 규칙으로 다시 해석&rsquo;** 을 누르면 입금으로 되살아난다.

본문이 JSON 이 아니어도 받는다. 알림 문구에 큰따옴표나 줄바꿈이 섞여 JSON 이 깨지는
경우가 흔하기 때문에, 파싱에 실패하면 본문 전체를 `raw` 로 취급한다.
그래서 `Content-Type: text/plain` 으로 알림 문구만 보내도 정상 동작한다.

## 구글폼 연동

스프레드시트가 여럿이어도 된다(참가자 폼 / 스태프 폼 …). 각각에
`apps_script/Code.gs` 를 설치하고 `INTAKE_ROUND` 만 다르게 준다. 참가자 동일성을
전화번호로 잡으므로 시트가 몇 개든 응답은 자동으로 합쳐진다.

1. 폼 응답 시트 → 확장 프로그램 > Apps Script → 코드 붙여넣기
2. 스크립트 속성 3개: `BACKEND_URL`, `INGEST_TOKEN`, `INTAKE_ROUND`(`earlybird` · `main` · `staff`)
3. **`previewMapping` 실행** — 각 컬럼이 어떤 필드로 잡히는지 로그로 확인 ★
4. `setupTrigger` 1회 실행 (제출 시 자동 전송)
5. `syncAll` 1회 실행 (기존 응답 일괄 반영)

### 이번 폼의 열이 어디로 가는가

`apps_script/` 의 응답 시트(`[이과대 X 공과대] 이공공이(2002) 참여자 모집`)를 기준으로
규칙을 맞춰 두었다. 스크립트 속성은 `BACKEND_URL` · `INGEST_TOKEN` · `INTAKE_ROUND=main`
셋이고, `previewMapping` 을 돌리면 아래 표대로 잡혀야 한다.

| 시트 열 | 필드 | 관리자 화면에서 |
|---|---|---|
| 타임스탬프 | `submittedAt` | 신청 시각 |
| 개인정보 · 초상권 동의서 | `portraitConsent` | '초상 이용' — 비동의면 촬영 주의 |
| 이름 · 학과 · 학번 · 전화번호 · 성별 | 그대로 | 신청 정보 |
| 총학생회비 납부여부 | `isCouncilMember` | 요금 구분 → 5,000 / 7,000원 |
| 참가비 입금 (안내문) | `declaredPaid` | 본인은 냈다는데 은행에 없으면 경고 |
| **1부 교류전 - 조장 지원 여부** | `leaderPreference` | **'조장 희망' · '조장 가능' 배지 + 필터**, 배정 탭 후보 목록에도 표시 |
| **솔로파티 참가 여부** | `joinsAfterparty` | 뒤풀이 배지 · 청구액에 +10,000 · 2부 출석 대상 |
| 솔로파티 사전 참여비 (안내 확인) | `afterpartyFeeAcknowledged` | 뒤풀이비 안내를 보낼 때 '처음 듣는 사람' 구별 |
| **닉네임** | `nickname` | 신청 정보 · 명찰 명단(`/roster`)에 함께 내려간다 |
| 태어난 년도 | `birthYear` | '2004년' · `2006.0` · '2007년도' 를 전부 2004 · 2006 · 2007 로 |

답변이 **문장**이라('납부하지 않았습니다' · '입금하였습니다' · '참여하겠습니다')
참/거짓 판정은 어미를 본다. 부정형('않았' · '않겠' · '하지않' · '아직')을 먼저 거르지 않으면
'납부하지 않았습니다' 가 '납부' 때문에 참이 된다. `tests/test_form_ingest.py` 의
`_festa_row` 가 실제 답변 문구 그대로 이것을 지킨다.

> 문항이 **없는** 폼(스태프 시트 등)에서는 값이 아예 오지 않고, 그때 백엔드는 기존
> 값을 건드리지 않는다 — 관리자가 화면에서 적어 둔 닉네임이나 켜 둔 뒤풀이가
> 재제출 한 번으로 풀려서는 안 된다.
>
> 응답 시트 파일 자체는 개인정보라 **커밋하지 않는다** (`.gitignore`).

### 왜 위치 기반으로 읽는가

`입금 완료 되셨을까요?` 컬럼이 **납부자용·미납부자용 두 개**이고 제목이 똑같다.
`e.namedValues` 는 질문 제목이 키라서 이런 경우 충돌한다. 그래서 헤더 행과 응답 행을
위치로 맞춰 읽고, 같은 제목의 컬럼은 비어 있지 않은 값을 골라 하나로 합친다.

### 스태프 시트

`INTAKE_ROUND=staff` 로 들어온 사람은 **받는 즉시 스태프**가 된다(`is_staff`). 스태프는
참가비가 다르고 럭키드로우에서도 빠지므로, 명단에 앉힌 뒤 관리자가 한 명씩 다시 눌러
주게 두면 그 사이의 집계가 어긋난다. 관리자 페이지에는 '스태프' 태그가 자동으로 붙는다.

- **켜기만 하고 끄지 않는다.** 같은 사람이 나중에 본모집 폼을 한 번 더 내도 지정이
  풀리지 않는다. 해제는 관리자 화면에서만 한다.
- 스태프 참가비는 대시보드에서 정한다. 정하기 전에는 예상 금액이 0원이라 '면제'로
  보이고, 금액을 넣는 순간 **이미 들어와 있던 스태프 전원에게 함께 반영**된다.
- 질문 구성이 참가자 폼과 거의 같아 `FIELD_RULES` 를 그대로 쓴다. 총학생회비 질문이
  없어 회비 구분이 비지만, 스태프는 요금 구분이 '스태프'라 쓰이지 않는다.

### 무엇을 가져오고 무엇을 버리는가

`FIELD_RULES` 에 명시된 항목만 전송한다. 규칙에 없는 컬럼은 보내지 않으므로,
폼에 질문이 추가되어도 모르는 데이터가 서버로 새어 들어가지 않는다.

가져오는 것 — 이름 · 학번 · 성별 · 전화번호 · 비상연락처 · 소속 · 지병 유무/병명/조치 ·
알레르기 · 총학생회비 납부 여부 · 입금 완료 응답 · 초상 이용 동의

**버리는 것 (DENY_RULES)**

| 항목 | 이유 |
|---|---|
| 주민등록번호 13자리 | **개인정보보호법 제24조의2** 상 법령에 구체적 근거가 없으면 처리 자체가 금지된다. 이 시스템은 이름·전화번호로만 매칭하므로 쓸 일도 없다 |
| 납부 증빙 스크린샷 | 구글 드라이브 링크. 필요하면 원본 시트에서 직접 본다 |

백엔드에도 같은 차단이 걸려 있다(`app/services.py` 의 `is_sensitive`). 키 이름뿐 아니라
**값이 주민번호 형태(6자리-7자리)이면 그것만으로도 버린다.** 이중 방어다.

### 헤더 매칭의 함정

헤더가 긴 안내문이라 단순 키워드 포함 검사는 위험하다.

```
'입금자명 : 성명+전화번호 뒷자리\n예시) 김공대0711...'
                ^^^^  ^^^^^^^^
```

이 헤더에는 '성명'과 '전화번호'가 모두 들어 있어 이름·전화번호 컬럼으로 오인될 수 있다.
그래서 앞부분 일치(`startsWith`)를 우선 쓰고, 필요하면 키워드 두 개를 함께 요구한다.
(`총학생회비` + `납부하셨` 처럼)

### 재제출 · 중복 신청

같은 전화번호로 다시 내면 새 참가자가 생기지 않고 최신 응답으로 갱신되며,
`submission_count` 가 올라간다. 두 시트에 모두 신청한 경우도 이걸로 드러난다.

**자연키는 전화번호다.** 이름·학번이 같아도 번호가 다르면 다른 사람으로 들어가고,
번호가 같으면 다른 이름이어도 같은 사람으로 합쳐진다. 번호 표기(`010-1234-5678` /
`01012345678` / `+82 10 1234 5678`)는 정규화되어 흡수된다.

> **재제출은 덮어쓰기다.** 폼에서 비워 둔 선택 항목은 Apps Script 가 아예 보내지 않고,
> 백엔드는 받지 못한 필드를 `None` 으로 채운다. 즉 **일부만 고쳐 다시 내면 첫 응답에
> 적었던 다른 값이 지워진다.** 정정할 때는 폼을 처음부터 전부 채워 내야 한다.
> (관리자가 손댄 값 — 스태프 지정 · 금액 강제 지정 — 은 재제출로 풀리지 않는다)

마감 후 `GET /api/admin/participants?resubmitted=true` 로 여러 번 낸 사람만 추려
지병·알레르기처럼 현장에서 중요한 항목을 원본 시트와 대조하는 것을 권한다.
관리자 화면의 **재제출** 필터가 같은 일을 한다.

## 참가비는 두 겹이다

본 행사비가 아래에 깔리고, **뒤풀이에 가는 사람만** 그 위에 뒤풀이비가 얹힌다.

| | 금액 | 정하는 곳 |
|---|---|---|
| 본 행사 · 총학생회비 납부자 | 5,000원 | `.env` 의 `FEE_COUNCIL_MEMBER` |
| 본 행사 · 총학생회비 미납부자 | 7,000원 | `.env` 의 `FEE_NON_MEMBER` |
| 본 행사 · 스태프 | 미정 | **관리자 > 입금 내역** |
| 뒤풀이 (참가자만) | +10,000원 | **관리자 > 입금 내역** (초기값 `.env` 의 `FEE_AFTERPARTY`) |

### 왜 갈라 세는가

**뒤풀이비는 별도 안내로 나중에 걷는다.** 두 겹을 한 덩어리로 세면 뒤풀이 신청자
전원이 안내가 나가기도 전에 &lsquo;미납&rsquo;으로 물들고, `is_settled` 가 막혀 **본 행사
참가 확정이 통째로 잠긴다.**

그래서 들어온 돈을 **본 행사비부터 채우고** 남는 것을 뒤풀이비로 넘긴다.

```
base_paid       = min(paid_amount, base_fee)
afterparty_paid = max(paid_amount - base_fee, 0)
```

- `payment_status` — **본 행사비** 기준. 확정 · 배정 · 출석의 문을 여는 것은 이 값뿐이다.
  (총액을 넘겨 들어왔을 때만 `OVERPAID` 다)
- `afterparty_status` — 뒤풀이비 기준. `NONE`(미참가) · `UNPAID` · `UNDERPAID` · `PAID`.
  화면에서는 배지로만 드러난다.

### 합산 납부 배지

안내가 나가기 전에 **이미 본 행사비와 뒤풀이비를 한 번에 보낸 사람이 있다.** 갈라 두지
않으면 그 사람에게 안내를 한 번 더 보내고, 받은 사람은 한 번 더 낸다.

`afterparty_prepaid` 는 **입금 1건**이 총 청구액을 덮었을 때만 참이다. 두 번에 나눠
낸 사람은 안내를 받고 낸 것이므로 해당하지 않는다.

관리자 > 참가자의 **&lsquo;뒤풀이비 미납&rsquo;** 필터가 곧 안내를 보낼 명단이고,
합산 납부자는 거기서 이미 빠져 있다.

### 매칭이 인정하는 금액도 하나가 아니다

뒤풀이 신청자가 지금 보낼 법한 금액은 셋이다 — 본 행사비만(안내 전), 뒤풀이비만
(안내 후), 둘을 합쳐서. 2단계에서 &lsquo;미납액과 정확히 같은가&rsquo;만 보면 셋 중 둘이
금액 불일치로 떨어져 확인 필요 큐에 쌓인다. `matching.plausible_amounts` 가 셋을 모두
인정한다.

### 화면에서 고치는 금액

스태프 참가비와 뒤풀이비는 늦게 정해지고 바뀌므로 `.env` 가 아니라 화면에서 고친다.
값은 `settings` 테이블에 남아 `.env` 보다 우선하므로, 한 번 정하면 재배포해도 유지된다.

- **금액을 바꾸면 해당하는 사람 전원의 예상 금액이 함께 따라간다**
  (`services.recalc_expected_amounts`). 한 명씩 다시 손보게 두면 금액이 섞인 채로 남아
  수납 집계가 어긋난다.
- 본 행사비가 0원이면 낼 것이 없으므로 **면제**로 잡힌다. 그러지 않으면 스태프 금액이
  정해지기 전까지 스태프 전원이 미납으로 떠 확인 필요 건에 섞인다.
- 스태프 지정은 관리자만 한다. 폼을 다시 제출해도 풀리지 않는다.

> ⚠️ `MINOR_DEPOSIT_THRESHOLD` 를 **참가비보다 낮게** 잡아야 한다. 참가비가 5,000원까지
> 내려가 예전 기본값(10,000)을 그대로 두면 정상 참가비가 통째로 &lsquo;기타 입금&rsquo;으로
> 갈린다. 지금 기본값은 3,000원이다.

## 현장 납부

당일 행사라 문 앞에서 참가비를 내는 사람이 반드시 나온다. 그때 계좌로 다시 보내게 하면
거래내역 파일을 또 내려받아 올릴 때까지 확정이 열리지 않아 줄이 선다.

`POST /api/admin/participants/<id>/onsite-payment` 가 받은 즉시 **입금 1건**으로 남긴다.
금액을 비우면 아직 안 낸 만큼을 그대로 채운다.

- 거래내역 업로드로 들어온 것과 **같은 테이블**에 들어가되 출처가 `onsite` 라, 정산할 때
  계좌로 들어온 돈과 손에 쥔 현금을 갈라 볼 수 있다.
- 자동 매칭에 태우지 않고(`run_match=False`) 바로 그 사람에게 연결한 뒤 `manual_locked`
  로 잠근다 — 누구에게서 받았는지 이미 알고 있다.
- 접수대에서 두 번 눌리는 사고는 흔하다. 같은 사람 · 같은 금액 · 같은 분이면 지문이
  겹쳐 **409 로 거절**된다.
- 누가 받았는지는 작업 기록(`deposit.onsite`)에 남는다.

## 관리자 계정 · 등급 · 역할군 · 탭 권한

관리자는 원래 하나였다. 비밀번호를 아는 사람은 모두 같은 `admin` 이었고 작업 기록도
그 한 이름으로 남았다 — 몇 달 뒤에 로그를 봐도 **누구였는지 알 수 없다**는 뜻이다.

### 무엇이 자물쇠이고 무엇이 이름표인가

```
등급     : 비밀번호가 갈린다 (.env 에 둘)     ← 진짜 문
로그인 ID : 사람마다 다름 (보통 본인 이름)     ← 누가 했는지 남기는 이름표
탭 권한   : 역할군 / 개인 지정                 ← 필요한 화면만 보이게 하는 정리
```

로그인은 **ID + 등급별 비밀번호**다. 비밀번호는 두 개다.

| 등급 | 누구 | `.env` 항목 |
|---|---|---|
| `lead` | 최고 관리자 · 국장단 (학생회장 · 국장 · 차장) | `ADMIN_PASSWORD_HASH` |
| `staff` | 국원 | `STAFF_PASSWORD_HASH` |

**계정의 등급과 입력한 비밀번호의 등급이 같아야만 들어온다.** 국원에게 알려 준
비밀번호로 국장 ID 를 넣어도 열리지 않고, 반대도 마찬가지다 — 어느 문에 어느 열쇠가
맞는지가 흐려지면 나눈 의미가 없다. 등급은 **역할군**에 매기므로(관리자 > 관리자 탭)
사람이 바뀌어도 역할군만 맞추면 되고, 역할군이 없는 계정은 국원으로 본다.

비밀번호는 **먼저 확인하고 계정을 찾는다.** 그래야 아무 비밀번호도 모르는 사람이
ID 만 넣어 보며 '누가 관리자인지'를 알아내지 못한다.

`STAFF_PASSWORD_HASH` 를 **비워 두면 국원도 국장단 비밀번호를 쓴다.** 등급을 나누기
전에 배포된 `.env` 를 아직 못 고쳤어도 아무도 문 밖에 서지 않게 하기 위함이다. 그
상태는 기동 로그에 경고로 남고, 관리자 화면에도 "아직 두 비밀번호가 갈리지 않았습니다"
라고 뜬다 — 나눴다고 믿는 채로 안 나뉜 상태가 제일 나쁘다.

같은 등급 안에서는 ID 가 자물쇠가 아니다. 그 층의 목적은 차단이 아니라 **작업 기록에
사람 이름을 남기는 것**이다.

- 최고 관리자 ID 는 `wont0309` 다. 기동할 때 없으면 만들어지고, **로그인 시점에도
  없으면 되살린다** — DB 를 직접 손대다 이 행이 사라지면 아무도 권한을 줄 수 없다.
- ID 는 느슨하게 맞춘다. 공백을 걷어내고 영문은 대소문자를 가리지 않는다
  (`홍 길동` = `홍길동`). 이름을 ID 로 쓰는 이상 띄어쓰기로 못 들어가면 안 된다.
- 계정을 지워도 **작업 기록에 남은 이름은 그대로다.** 로그는 그 자체로 완결된 기록이다.

### 권한은 두 단계

```
역할군 (학생회장 · 국장 · 차장 · 국원)   ← 사람이 바뀌어도 그대로인 것. 등급도 여기서 정한다
  └ 개인 지정                            ← 그 사람만 예외로 둘 때
```

역할의 탭을 고치면 그 역할을 쓰는 사람 전원의 화면이 함께 바뀐다. 개인 지정이 있으면
그것이 이긴다. **탭 권한은 화면을 정리하는 것이지 API 를 막는 것이 아니다** — 목록을
가려도 로그인한 사람은 API 를 부를 수 있다. 다만 **관리자·역할군을 다루는 길만은
서버에서 최고 관리자로 막는다**(`require_super`). 권한을 스스로 올리는 길까지 열어
두면 구분 자체가 무의미해지기 때문이다.

권한과 이름은 **요청마다 DB 에서 다시 읽는다.** 토큰에 박아 두면 권한을 내리거나
계정을 껐을 때 상대가 로그아웃할 때까지 그대로다.

탭 목록(`app/admins.py` 의 `TABS`)과 등급 목록(`TIERS`)은 서버가 단일 진실이다.
프론트는 세션 응답이 돌려준 탭만 그린다.

역할군의 등급을 옮기면 **그 역할군의 사람 전원이 다른 비밀번호로 로그인하게 된다.**
화면에서 한 번 더 묻고, 작업 기록에도 등급 변경으로 남는다.

등급 컬럼(`admin_roles.tier`)은 뒤늦게 붙었다. 쓰던 DB 의 역할군은 값이 비어 있는데,
기동할 때 `ensure_role_tiers()` 가 **이름을 보고** 기본 역할군의 등급을 되살린다
(학생회장·국장·차장 → 국장단, 그 외 → 국원). 한 번 채운 뒤에는 건드리지 않는다 —
화면에서 내린 등급이 기동할 때마다 되살아나면 고칠 방법이 없어진다.

## 작업 기록

감사 로그는 몇 달 뒤에 "이거 누가 왜 이렇게 했지" 를 되짚는 데 쓴다. 그래서 한 줄에
**누가 · 누구를 · 무엇을 · 무엇에서 무엇으로** 가 모두 들어간다.

```json
{
  "action": "participant.update",
  "actor": "홍길동",
  "detail": {
    "target": "홍길동",
    "changes": [
      { "label": "요금 구분", "from": "총학생회비 납부자", "to": "스태프" },
      { "label": "참가비",    "from": "5,000원",          "to": "3,000원" }
    ]
  }
}
```

- **표시 문구는 백엔드가 만든다.** 기록은 그 자체로 완결되어야 하므로, 나중에 화면의
  라벨이 바뀌어도 예전 기록은 그때의 표현대로 읽혀야 한다. 상태 코드(`WAIVED`)가
  아니라 사람 말(`면제`)로 남기는 이유다.
- **값이 그대로면 기록하지 않는다.** '수정'을 눌렀지만 아무것도 안 바뀐 요청까지
  남으면 로그가 잡음으로 차서 정작 볼 것을 못 찾는다.
- 전후가 없는 단발성 기록(`재매칭 12건`)은 `from` 이 `null` 이다.

## 참가 확정 · 현장 배정 · 출석

입금 확인 다음에 오는 단계다. **앞 단계를 건너뛰면 뒷 단계가 열리지 않는다.**

```
납입 완료 ──▶ 참가 확정 ──▶ 조 배정 ──▶ 당일 체크인 (본 행사 · 뒤풀이)
```

### 왜 확정을 자동으로 하지 않는가

돈이 들어왔다는 것과 학생회가 참가를 인정했다는 것은 다르다. 입금자명이 어긋난 건,
정원 초과, 취소 요청이 섞여 있어 **명단은 사람이 한 번 봐야 한다.** 그래서 확정은
관리자가 누르는 별도 단계이고, `confirmed_at` 에 그 시점이 남는다. 뒤늦게 환불이나
정정이 생겨도 '언제 확정했는가'는 지워지지 않는다.

참가자 화면(`/payment`)에는 **납입 완료**와 **참가 확정**이 따로 보인다. 입금이 확인됐는데
확정 전이면 &lsquo;확정 대기 중&rsquo;으로 표시해, 무언가 잘못된 줄 알고 문의하는 일을 줄인다.

관리자 페이지 → 참가자 탭에서 한 명씩, 또는 **&lsquo;전원 참가 확정&rsquo;** 으로 납입이 끝난
미확정자를 한 번에 처리한다. 납입이 끝나지 않은 사람은 조용히 건너뛰고 몇 명이
걸러졌는지 알려준다.

### 폼을 내지 않은 사람 (참가자 수기 등록)

현장 합류 · 대리 신청 · 폼 응답 유실로 명단에 없는 사람이 반드시 나온다. 입금 수기
등록과 같은 이유로 명단에도 손으로 넣는 길을 둔다 — 관리자 페이지 → 참가자 →
**&lsquo;참가자 수기 등록&rsquo;** (`POST /api/admin/participants`).

- **전화번호가 자연키다.** 이미 있는 번호면 `409 duplicate_phone` 으로 거절한다.
  폼으로 들어온 사람을 손으로 한 번 더 넣어 두 사람이 되는 것이 여기서 가장 흔한 사고다.
- 나중에 같은 번호로 폼 응답이 도착하면 새 행이 생기지 않고 이 행이 갱신된다
  (`services.upsert_participant`). 손으로 넣어 둔 것이 중복으로 남지 않는다.
- 등록 직후 **미매칭 입금을 다시 태운다.** 이 사람 이름의 입금이 먼저 들어와 있었다면
  등록과 동시에 붙는다. 폼이 늦게 도착했을 때와 같은 처리다.
- 참가비는 요금 구분에서 자동으로 정해진다. 등록한 사실은 `participant.create` 로 남는다.
- 학번을 비우면 **셀프 체크인이 되지 않는다** (본인 확인이 이름 + 학번 + 전화 뒷 4자리라서).
  현장에서 스태프가 출석 처리하면 된다.

### 잘못 적어 낸 신청 정보 고치기

학번 칸에 생년월일, 이름 오타, 번호 한 자리 누락 — 폼에 잘못 적어 내는 사람이 반드시
나온다. 관리자 페이지 → 참가자 → 사람을 펼쳐 **&lsquo;정보 수정&rsquo;** 에서 이름 ·
전화번호 · 학번 · 학과 · 성별 · 비상 연락처를 고친다 (`PATCH /api/admin/participants/<id>`).

- **학번을 고쳐 두지 않으면 당일 문 앞에서 튕긴다.** 셀프 체크인의 본인 확인이
  이름 + 학번 + 전화 뒷 4자리이기 때문이다.
- 이름 · 전화번호는 매칭 근거다. 고치면 `name_norm` · `phone_last4` 를 함께 맞추고
  **미매칭 입금을 다시 태운다** — 이름을 잘못 적어 붙지 못했던 입금이 정정과 동시에 붙는다.
  이미 확인 완료거나 손으로 고정한 입금은 건드리지 않는다.
- 전화번호는 자연키라 다른 사람이 쓰고 있으면 `409 duplicate_phone` 으로 거절한다.
  이름을 비우는 것도 받지 않는다.
- 고친 내용은 무엇을 무엇에서 무엇으로 바꿨는지 `participant.update` 로 남는다.
  전화번호만은 로그에 가리지 않고 남긴다 — 가리면 가운데 자리만 고친 정정이
  &lsquo;바뀐 것이 없다&rsquo;로 보여 기록 자체가 사라진다.

> **폼 응답이 다시 들어오면 폼 값이 이긴다.** `upsert_participant` 는 이름 · 학번 ·
> 학과 · 성별 · 비상 연락처를 매번 폼 응답으로 덮는다. 정정한 사람이 폼을 또 내거나
> 시트 전체를 다시 흘려보내면 고친 값이 되돌아가므로, 정정은 접수가 끝난 뒤에 하고
> 마감 후에는 전체 재동기화를 돌리지 않는 편이 안전하다.

### 배정 항목은 데이터다

**기본 항목은 조 하나뿐이다.** 당일 행사라 숙소 호수도 버스도 없다. 그래도 운영을
시작하면 분류가 더 필요해지므로(자리, 조끼 색, 담당 스태프…) 그때마다 컬럼을 늘리고
재배포하는 대신 **무엇을 배정하는가 자체를 `assignment_fields` 테이블에 둔다.**

- 관리자 페이지 → 배정 → **+ 항목 추가** 로 늘린다. 재배포가 필요 없다.
- 값은 `participants.assignments_json` 한 칸에 모이므로 항목이 늘어도 스키마는 그대로다.
- 조는 **선택지**다. **조를 하나 만드는 일**은 &lsquo;조&rsquo; 항목의 선택지에 한 줄
  넣는 것과 같다. 손으로 적게 두면 `1조` / `1` / `一조` 가 섞여 조별 인원이 어긋난다.
- 조는 `is_system` 으로 잠겨 있어 지우거나 끌 수 없다.
  조 단위 집계와 CSV 고정 열이 이 항목을 전제로 한다.
- 이미 배정된 선택지는 지울 수 없다. 지우면 그 사람의 조가 유령이 되기 때문이다.

기본 항목의 **종류(자유 입력 ↔ 선택지)를 바꾸면 기동 시 기존 DB 도 따라온다.**
새 코드가 기존 DB 위에 올라가는 배포 방식이라, 맞춰 주지 않으면 새로 설치한 곳과
이미 돌던 곳의 동작이 갈린다. 자유 입력 → 선택지로 바꿀 때는 **이미 적혀 있던 값을
먼저 선택지로 끌어올린 뒤** 종류를 바꾸므로, 기존 배정이 고를 수 없는 값이 되지 않는다.
라벨과 선택지는 학생회가 화면에서 고친 것이라 시드가 덮어쓰지 않는다.

`group_no` 컬럼은 조 단위 집계와 인덱스 검색을 위한 **사본**이다.
쓰기는 `app/assignments.py` 의 `apply_assignments` 한 곳에서만 일어난다.

### 조를 짤 때는 방향이 반대다 (항목별 일괄 배정)

배정 탭에는 세 화면이 있다.

| 화면 | 방향 | 쓰는 때 |
|---|---|---|
| 엑셀로 한 번에 배정 | 파일 → 명단 | **편성을 이미 엑셀에서 끝냈을 때** |
| 항목별 일괄 배정 | 값 → 사람 | **조 짜기.** &lsquo;1조&rsquo;를 정해 두고 들어갈 사람을 모은다 |
| 참가자 배정 | 사람 → 값 | 한 사람의 배정을 한꺼번에 손볼 때 |

조를 짜는 일은 사람마다 드롭다운을 열어 **같은 값을 반복해서 고르는** 작업이라
사람 수만큼 손이 간다. 그래서 값을 먼저 고르고 → 이름 · 학번 · 학과 · 전화번호로
검색해 → 체크한 뒤 한 번에 배정하는 길을 따로 둔다. 선택지 옆에는 현재 인원이
함께 나오고, 이미 그 값인 사람은 후보 대신 &lsquo;현재 인원&rsquo;에 모여 거기서 뺄 수 있다.

전용 API 는 없다. `PATCH /api/admin/participants/<id>` 를 사람 수만큼 부르는 화면일
뿐이고, 중간에 하나가 실패해도 나머지는 계속 넣은 뒤 누가 안 됐는지 이름으로 알린다.

### 엑셀 왕복 (`app/assignment_sheet.py`)

조 편성은 대개 엑셀에서 끝난다. 명단을 늘어놓고 자르고 붙이며 짠 결과를 화면에서
한 명씩 다시 고르게 두면 편성을 두 번 하는 셈이다. 그래서 **명단 그대로 양식을
내려받아 값만 채워 올리는** 길을 둔다.

- `GET /api/admin/assignments/template.xlsx` — 지금 확정자 명단과 항목 정의로 만든다.
  **고정된 서식 파일을 두지 않는다.** 항목이 운영 중에 늘어나므로(텐트·차량·조끼)
  양식의 열도 그때의 `assignment_fields` 를 보고 만들어야 한다.
- 이미 배정된 값은 채워서 내려준다. 파일 하나로 &lsquo;지금 어디까지 짜였는지&rsquo;를
  볼 수 있고, 고쳐서 다시 올리는 것이 자연스럽다.
- **선택지가 있는 항목은 엑셀 드롭다운으로 걸어 둔다.** 목록은 숨긴 시트(`선택지`)에
  적고 범위로 가리킨다 — 수식에 직접 박으면 255자 제한에 걸려 조가 20개만 넘어도 넘친다.
  값을 손으로 적게 두지 않는 것이 배정 설계의 전제라, 파일 단계에서도 지킨다.
- `사용법` 시트에 규칙과 현재 선택지를 함께 적어 보낸다.

`POST /api/admin/assignments/import` 로 되받는다 (xlsx / csv).

- **빈 칸은 건드리지 않는다.** 아직 안 짠 사람이 그대로 남아 있는 것이 보통이고,
  반쯤 채운 파일을 올렸다고 나머지 배정이 지워지면 안 된다. 풀려면 `-` 또는 `미배정`.
- 사람은 **참가자ID → 학번 → 이름** 순으로 찾는다. 뒤로 갈수록 흔들리는 값이라
  **여럿에 걸리면 고르지 않고 건너뛴다.** 엉뚱한 사람을 조에 넣는 것보다 낫다.
- 값 하나가 선택지에 없으면 **그 행만** 통째로 넘어간다. 반쯤 반영된 행을 남기면
  무엇을 다시 채워야 하는지 알 수 없다.
- 확정 전인 사람은 건너뛰고 몇 행이 왜 걸렸는지 돌려준다.
- 감사 로그는 한 줄씩 `participant.update` 로 쪼개지 않고 `assignment.import` 하나에
  &lsquo;누구의 무엇이 무엇에서 무엇으로&rsquo;를 모은다 (100줄까지, 넘으면 줄여서 기록).

### 출석 회차 — 하루인데 두 번 일어난다

낮의 **본 행사**가 있고, 신청자 중 일부만 남는 **뒤풀이**가 저녁에 따로 있다.
두 자리는 인원도 여닫는 시각도 다르다.

이것을 참가자 테이블의 불리언 두 개로 두면 회차가 하나 늘 때마다 컬럼을 늘리고
재배포해야 한다. 그래서 배정 항목과 같은 방식을 쓴다 — **무엇을 세는가 자체를 데이터로
둔다**(`CheckinSession`, `app/attendance.py`). 현장에서 &lsquo;2부도 따로 세자&rsquo;가
나와도 화면에서 회차를 하나 더 만들면 끝이다.

| 회차 | `key` | 대상 | 번호 발급 |
|---|---|---|---|
| 본 행사 | `main` | 확정자 전체 | ○ (`gives_draw_no`) |
| 뒤풀이 | `afterparty` | **뒤풀이 신청자만** (`afterparty_only`) | × |

`main` 만 `is_system` 으로 잠근다. 럭키드로우 번호와 참가자 사본 컬럼
(`checked_in_at`)이 이 회차 하나를 전제로 하고 있어, 지우면 출석 현황이 통째로 빈다.

### 두 갈래로 들어온다

- **셀프** — 입구에 QR(`/checkin`)을 붙여 두고 참가자가 직접 찍는다. 성공하면 이름과
  조가 크게 뜨고, 그 화면을 스태프에게 보여 주면 명찰과 간식을 받는다.
- **수동** — 관리자가 명단에서 이름을 찾아 누른다(`POST /api/admin/attendance/check`).
  **창구가 닫혀 있어도 된다** — 사람이 직접 확인하고 누르는 것이기 때문이다.
  인원이 적고 자리가 어수선한 뒤풀이는 대개 이쪽만 쓴다.

어느 쪽으로 들어왔는지는 `CheckIn.by` 에 남는다. 회차 × 참가자 한 쌍에 한 행뿐이라
두 번 찍혀도 행이 늘지 않고, **처음 들어온 시각을 덮어쓰지 않는다** — 그 순서가 곧
럭키드로우 번호의 근거다.

**본인 확인은 이름 + 학번 + 전화번호 뒤 4자리** 세 가지다. 이름만으로는 동명이인을
가를 수 없고, 학번은 같은 과 학생끼리 서로 아는 경우가 많아 둘만으로는 대리 체크인을
막지 못한다.

| 상황 | `reason` | 화면 |
|---|---|---|
| 세 가지가 모두 일치 | `ok` | 회차 이름 + 이름 + 조 + 번호 |
| 이미 체크인함 | `ok` (`alreadyCheckedIn`) | 같은 화면 — 다시 봐야 명찰을 받는다 |
| 하나라도 다름 | `not_found` | 스태프 문의 안내 |
| 확정 전 | `not_confirmed` | 스태프 문의 안내 |
| 뒤풀이 미신청자가 뒤풀이 회차에 | `not_in_session` | 스태프 문의 안내 |
| 열린 회차가 없음 | `closed` | 시각 안내 |

### QR 은 하나이고 자리는 여럿이다

참가자는 회차를 고르지 않는다. 같은 입구 QR 로 들어와 **그때 열려 있는 회차**에 찍힌다.
그래서 **한 번에 하나만 열린다** — 하나를 열면 서버가 나머지를 닫는다. 둘이 동시에
열려 있으면 어디에 찍힌 것인지 알 수 없다.

같은 이유로 체크인 성공 화면 맨 위에 **회차 이름**을 띄운다. 말해 주지 않으면 참가자는
자기가 어디에 찍힌 것인지 알 수 없다.

> **체크인 창구는 기본이 닫힘이다.** QR 인쇄물은 행사 며칠 전부터 돌아다니므로,
> 열어 두면 시작 전에 원격으로 출석 처리해 버리는 사람이 생긴다.
> 관리자 페이지 → 출석 → **체크인 열기** 를 당일에 누른다.

rate limit 은 조회(10회/10분)와 달리 넉넉하다(`CHECKIN_RATE_LIMIT`, 기본 300회/10분).
행사장에서는 수백 명이 같은 기지국·와이파이를 타 IP 가 통째로 겹치기 때문에,
조회와 같은 값을 걸면 정상 체크인이 줄줄이 막힌다.

### 출석 현황

분모는 신청자가 아니라 **참가 확정자**다. 확정되지 않은 사람은 체크인 자체가 막혀 있어,
전체 신청자를 분모로 잡으면 출석률이 영원히 100%에 닿지 않는다.
**뒤풀이 회차는 분모가 한 번 더 좁아진다** — 뒤풀이를 신청한 확정자만이다.

`GET /api/admin/attendance?session=<회차 key>&groupBy=<항목 key>` 로 회차와 기준을
고른다. 배정이 없는 사람은 &lsquo;미배정&rsquo; 묶음으로 따로 모인다.

## 개인 QR · 명찰

명찰 뒷면의 QR 이 가리키는 **개인 카드**(`/p/<token>`)가 이 절의 전부다. 지난 행사에
있던 외출 태그(문 앞 스태프가 QR 을 찍어 출입 이력을 남기는 것)는 **이번 행사에 없다** —
당일에 끝나 숙소가 없으므로 드나들 문이 없다. 스캐너 화면과 `outing_logs` 테이블은
코드에서 통째로 걷어냈다.

### 토큰은 참가자 id 가 아니다

`Participant.card_token` 은 무작위 8자(헷갈리는 0·O·1·I 를 뺀 32자에서 뽑는다)다.
id 를 그대로 쓰면 `1`, `2`, `3` … 이 눈에 보여 남의 카드를 열어 보는 장난이 가능하다.
무작위 값은 비용이 들지 않는다.

**한 번 준 토큰은 바꾸지 않는다.** 명찰에 인쇄되어 목에 걸려 있기 때문이다.
토큰은 두 자리에서 발급된다 — 명찰 명단을 받을 때(`GET /api/admin/roster`)와,
셀프 체크인에 성공할 때. 뒤쪽이 있는 이유는 명찰을 나눠 주지 못한 사람도 체크인만
하면 폰으로 자기 카드를 띄울 수 있어야 하기 때문이다.

### 카드에 담기는 것

**여기서 새로 드러나는 정보는 없다.** 이름 · 학과 · 조는 명찰 앞면에 이미 인쇄되어
있고, 이 주소는 그 명찰을 손에 든 사람만 안다. 전화번호 · 건강 정보 · 납입 내역처럼
명찰에 없는 것은 서버가 아예 내려주지 않는다.

회차별 출석 기록(본 행사 · 뒤풀이)은 담는다. 뒤풀이 자리로 옮기면서 "내가 찍혔나"를
묻는 사람이 반드시 나오고, 그 답은 본인의 것이다.

### 명찰 인쇄

`GET /api/admin/roster` 가 확정자 명단에 개인 토큰을 붙여 내려준다. 실제로 그리는 일은
프론트가 한다([FrontEnd/README.md](../FrontEnd/README.md#명찰)).

> 이번 행사는 **명찰 디자인과 글꼴이 통째로 바뀐다.** 새 시안을 받기 전까지
> 프론트의 인쇄 화면은 잠겨 있다 — 그리는 코드가 멀쩡해서 누르면 지난 행사의 서식이
> 그대로 나오고, 인쇄소로 넘어가면 되돌릴 수 없기 때문이다.

## 럭키드로우

### 번호는 체크인 순서다

참가자가 체크인하면 그 순서대로 `001`, `002`, `003` … 이 발급된다(`participants.draw_no`).
미리 뽑기표를 뿌리지 않아도 되고, 참가자는 체크인 화면에 뜬 자기 번호만 기억하면 된다.
셀프 체크인과 스태프 대행 처리 어느 쪽이든 똑같이 받는다.

- **한 번 받은 번호는 회수하지 않는다.** 스태프가 출석을 취소해도 번호는 그 사람 것으로
  남는다. 번호를 재사용하면 자기 번호를 외운 채 추첨 화면을 보고 있는 사람과 어긋난다.
  대신 그 번호는 **후보에서 빠진다**(`out: "not_checked_in"`).
- 유일성은 `uq_participants_draw_no` 인덱스가 보장한다. 발급이 부딪히면 최댓값을 다시
  읽어 재시도한다. 번호 발급은 **체크인을 커밋한 뒤에** 하므로, 발급이 실패해도
  체크인은 유효하다 (화면을 다시 열면 번호를 받는다).

> SQLite 의 `ALTER TABLE ADD COLUMN` 은 UNIQUE 제약을 붙일 수 없다. 그래서 이 유일성은
> 컬럼이 아니라 **별도 인덱스**로 선언되어 있고, `ensure_schema` 가 기동할 때 빠진
> 인덱스까지 만들어 준다 (`create_all()` 은 기존 테이블을 건너뛰기 때문에).

### 상품은 미리 등록해 둔다

행사 전에 `1등 에어팟 1개 · 2등 텀블러 3개 · 간식 10개` 를 목록으로 넣어 두고
(`PUT /api/admin/draw/prizes`), 당일에는 회차마다 고르기만 한다. 진행자가 매번
이름을 타이핑하게 두면 `1등 에어팟` 과 `1등에어팟` 이 섞여 남은 수량이 어긋난다.

- 목록은 `settings` 테이블에 JSON 으로 들어간다. 순서 있는 짧은 목록이라 관계를
  맺을 것이 없고, 진행 중에 통째로 갈아끼우는 편집이 더 자연스럽다.
- **집계는 이름이 아니라 `prize_id` 로 센다.** 상품 이름을 고쳐도 이미 나간 개수가
  따라온다. 반대로 `lucky_draws.prize` 에는 **그때의 이름이 그대로 박힌다** —
  목록에서 상품을 지워도 "그때 무엇을 걸었는가"는 남아야 한다.
- 준비한 개수를 넘겨 뽑으려 하면 `prize_exhausted` 로 막는다. 시상식에서 물건이
  모자라는 것이 화면에서 막히는 것보다 훨씬 곤란하다.
- 상품을 고르지 않고 뽑을 수도 있다. 그때는 수량 제한이 없다.

### 추첨은 뽑는 순간 결정된다

`POST /api/admin/draw` 를 부르면 서버가 **실제로 발급된 번호 중에서** `secrets.choice` 로
하나를 골라 `lucky_draws` 에 박고, 그 결과를 돌려준다. 화면의 슬롯머신은 이미 정해진
번호를 자릿수별로 드러내는 **연출**이다.

거꾸로(화면에서 무작위로 돌려 나온 값을 결과로 삼기) 만들면 두 가지가 터진다.

- 250명이 체크인한 자리에서 287번이 나온다.
- "마음에 안 드니 한 번 더" 가 흔적 없이 가능해진다.

응답의 `state.pool` 은 **뽑기 전** 판이다. 뽑은 뒤의 판을 주면 당첨자 타일이 이미
&lsquo;당첨됨&rsquo;으로 흐려진 상태에서 그 번호가 나와, 화면이 스스로 답을 부정한다.

### 후보

| 빠지는 이유 | `out` | 언제 |
|---|---|---|
| 출석 취소 | `not_checked_in` | 번호는 있지만 본 행사 체크인 기록이 지워졌다 |
| 참가 취소 | `cancelled` | |
| 그 자리에 없음 | `not_in_session` | `poolSession=<회차>` 로 후보를 좁혔을 때 |
| 스태프 | `staff` | `excludeStaff=true` 일 때만 |
| 이미 당첨 | `already_won` | 기본값. `allowRepeat=true` 로 풀 수 있다 |

**번호는 하나, 후보는 자리마다.** 번호는 본 행사 체크인 순서로만 준다 — 회차마다 새로
매기면 참가자가 번호를 두 개 외워야 한다. 뒤풀이에서 뽑을 때는 같은 번호를 쓰되
`poolSession=afterparty` 로 **그 자리에 남은 사람으로 후보를 좁힌다.** 낮에만 왔던
사람의 번호는 번호판에서 처음부터 꺼져 있어, 참가자는 자기가 후보인지 한눈에 안다.

`pool` 의 타일에는 **번호만 담는다.** 추첨 화면은 스크린에 띄우는 것이라 이름을 함께
내리면 명단이 그대로 공개되는 셈이 된다.

### 무효 처리

당첨자가 자리에 없으면 `POST /api/admin/draw/<id>/void` 로 무효로 돌린다.
**행을 지우지 않고 표시만 남긴다** — 누가 언제 왜 무효로 했는지가 보여야 뒷말이 없다.
무효가 되면 그 사람은 다시 후보가 되고 회차 번호도 비워진다(`round_no` 는 무효 건을
세지 않으므로 &lsquo;1등·2등&rsquo; 순서가 흐트러지지 않는다).

### 시연 흔적 지우기

행사 전에 몇 번 돌려 보고 나면 그 기록이 이력에 남는다. 무효 처리로는 지워지지
않는다 — 무효는 '이런 일이 있었고 취소했다'를 남기는 것이라, 시연 기록이 쌓인 채
본 추첨이 시작된다. 그래서 `DELETE /api/admin/draw` 로 **당첨 기록을 통째로 지운다.**
상품 수량과 후보가 처음 상태로 돌아간다.

- **되돌릴 수 없다.** 대신 무엇을 지웠는지가 감사 로그(`draw.clear`)에 남는다.
  기록을 지운 행위 자체가 기록의 일부이고, 그것까지 지울 수 있으면 이력이 의미를 잃는다.
- **번호(`participants.draw_no`)는 건드리지 않는다.** 번호는 체크인의 부산물이라
  출석 기록과 함께 있어야 한다. 여기서 같이 지우면 '체크인은 되어 있는데 번호가
  없는' 상태가 되어, 자기 번호를 이미 본 사람과 어긋난다. 시연용 체크인을 되돌리려면
  관리자 &gt; 출석에서 출석을 취소한다 (번호는 그 사람 것으로 남고 후보에서만 빠진다).

추첨 · 무효 · 전체 삭제는 모두 감사 로그(`draw.create` · `draw.void` · `draw.clear`)에 남는다.

## 개인정보 보호

- 본인 조회는 **이름 + 전화번호 전체**가 모두 일치해야 하고, 응답에는 본인 1건만 담긴다.
- 이름은 마스킹(`홍*동`)해 돌려주므로, 번호를 안다고 실명을 새로 알아낼 수는 없다.
- 명단을 나열하는 공개 엔드포인트는 존재하지 않는다.
- 조회 실패와 미신청은 **같은 응답**을 준다 (전화번호 존재 여부가 새지 않도록).
- 조회는 IP 기준 rate limit(기본 10회/10분)이 걸리고, 시도는 `lookup_attempts` 에 남는다.
- 관리자 비밀번호는 scrypt 해시만 저장하며 평문은 서버 어디에도 없다.
- 관리자 수동 조작은 전부 `audit_logs` 에 기록된다.
- 개인 카드(`/api/p/<token>`)는 **명찰에 이미 인쇄된 것**만 담는다. 토큰은 무작위라
  훑어 낼 수 없고, 명찰을 주운 사람이 볼 수 있는 것은 명찰을 읽는 것과 다르지 않다.
- 출석 기록은 **행사 자리별 참석 확인이지 위치 추적이 아니다.** 목적 밖으로 쓰지 않고,
  행사 종료 후 언제 지울지를 미리 정해 둘 것.
